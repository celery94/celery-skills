# Image Card

把 URL 内容做成一组原生 AI 生成的 **4:5 信息卡**，而不是 HTML 信息卡截图，也不是高密度长文海报。

默认目标是“**2-3 张就把重点讲明白**”的 editorial information card：保留留白、层级和传播感，同时让每张图都带走有效信息，而不是只有标题、数字和装饰主体。

默认产物是一组 **4:5** 竖版图片，落盘到：

`outputs\image-cards\[YYYYMMDD]-[topic]\`

目录内至少保留：

- `brief.json`：来源、提炼结果、图片顺序、每张图 prompt、发布文案
- `card-01.png`、`card-02.png` ...：最终图片

如果用户没有特别说明，默认在图片生成完成后继续：

1. 调用 `wechat-draft` 发布到公众号草稿箱（`newspic`）
2. 调用 `xiaohongshu-publisher` 发布小红书图文

如果用户明确说 **只生成**、**只发微信**、**只发小红书**，按用户要求覆盖默认行为。

## 执行节奏

1. **先读内容再定图组**：不要边读边生成。先把 URL 内容提炼成完整的 image brief，再批量生成。
2. **不要回到 HTML 截图链路**：这个 skill 的产物是原生 AI 生图，不要生成 `card.html`，也不要调用 `info-card-designer` 的导出流程。
3. **优先使用 Image Gen 技能**：默认优先用 `imagegen` 生成整组图片；只有在 `imagegen` 不可用、连续失败，或用户明确指定 Azure 时，才回退到 `azure-image-gen`。
4. **默认做短卡组，不拉成长组图**：除非用户明确要求更多页数，否则默认按 `2-3` 张完成叙事，不用 `4-6` 张慢慢铺开。
5. **默认中等偏上的信息密度**：内容规划阶段参考 `info-card-designer` 的压缩方式，先做出完整的编辑 brief，再翻译成生图 prompt；每张图都要有结论、解释和支撑，而不是只留一个大标题。
6. **先跑一轮中等质量**：默认先生成整组图片，只有个别卡片明显失败时，再单独重生成那几张。
7. **发布只复用现有两个 skill**：发布阶段只用 `wechat-draft` 与 `xiaohongshu-publisher`，不要再额外设计新的发布链路。

## 输入范围

必需输入：

- 一个 URL

可选补充要求：

- 风格：如“偏科技感”“杂志感”“偏投资人 deck 审美”“更生活方式”
- 受众：如“给创业者看”“面向产品经理”“适合公众号读者”
- 语气：如“冷静、克制”“更兴奋一点”“更适合转发”
- 信息密度：如“再多一点信息”“保持简洁”“偏轻量 deck”
- 图片数：如“控制在 2 张”“做成 4 张”
- 发布范围：只生成 / 只发微信 / 只发小红书 / 默认双发
- 生图后端：默认 `imagegen`，也可用户明确指定 `azure-image-gen`

如果用户没有额外要求，默认使用：

- **输出语言**：简体中文。无论来源 URL 是中文、英文还是其他语言，`brief.json`、图片可见文字、发布标题和发布摘要都默认写成自然的中文；只有用户明确要求其他语言时才改用对应语言。
- **风格**：高级 editorial information card / Swiss grid / 数据海报感
- **图片数**：默认 **3 张**；只有内容极短、结构单一时才缩到 **2 张**
- **信息密度**：默认 `medium`
- **生图尺寸**：`1024x1280`
- **输出格式**：PNG
- **后处理**：默认保留原始 4:5 尺寸与清晰度

如果用户明确要求 4 张或更多，按用户要求扩展；否则不要把正常文章默认拉回 `4-6` 张。

## Step 1：抓取 URL 内容

### 1.1 主抓取链路

优先使用 **Chrome DevTools MCP** 打开 URL 并提取正文。

如果 Chrome DevTools MCP 只能拿到导航、登录壳层、推荐流、页脚或空白骨架，视为抓取失败，进入回退链。

### 1.2 回退链

| URL 类型                                     | 回退链                                      |
| -------------------------------------------- | ------------------------------------------- |
| `arxiv.org/abs/`                             | `arxiv.org/html/{id}v1` → `r.jina.ai` + PDF |
| `x.com` / `twitter.com` / `mp.weixin.qq.com` | `r.jina.ai`                                 |
| 其他网页                                     | `r.jina.ai` → `defuddle`                    |

如果主抓取和回退链都拿不到可用正文，直接失败，不进入生图阶段。

## Step 2：把文章压缩成 image brief

目标不是复述全文，而是做成一组 **2-3 张中等偏上密度信息卡**：让读者只看这组图，也能知道“这篇内容为什么值得转发”，并且在快速翻看时能拿到结论、机制和最关键的事实。

默认先把来源内容转写为中文编辑 brief，再进入分页和 prompt 编写。英文或其他语言来源只作为事实来源，不应把英文标题、英文 bullet、英文长句直接带入图片，除非它们是不可翻译的产品名、模型名、论文名、公司名或行业术语。

### 2.1 提炼规则

内容提炼方式参考 `info-card-designer`，但产物仍然是原生 AI 生图而不是 HTML 卡片。先在内部把文章压成可发布的编辑 brief，再把 brief 翻译成图片。

先内部完成以下提炼，不要把中间分析大段展示给用户：

1. 抓 **最反直觉或最值得转发的结论**，作为整组图的主 hook
2. 先压出 **4-6 个源要点**，每个要点最多 `2` 句；再从中挑 `2-3` 个最该上图的要点，不要直接从原文跳到 prompt
3. 识别每个要点的角色：问题 / 背景 / 机制 / 证据 / 转折 / 结论 / 启示，避免整组图全是“功能描述”或“结果描述”
4. 记录最关键的数字、百分比、倍数、时间线和命名概念
5. 抽 `1` 句最有冲击力的话，作为可选 `quote_text` 或收尾页语义锚点；可重写表达，但不能改事实
6. 写出真正可发布的 `publish_title`、`publish_summary`、`closing_note`，不要把这些留到最后临时拼
7. 决定哪些信息适合进入图片，哪些只进入发布文案
8. 确定整组图的统一视觉语气、主色方向和版式气质

补充约束：

- 主标题必须是**结论句**，而不是主题名复述
- 产品 / 工具 / 模型 / 项目类内容：主体名必须进入封面主标题或副标题，不能只在角落 label 中出现
- 如果提炼后出现 `4` 个以上同类要点，先合并同类，再补足“问题 / 洞察 / 证据 / 收束”弧线

### 2.2 叙事弧线与分页职责

默认沿用 `info-card-designer` 的编辑式排序思路：前面制造疑问，中间解释机制，最后做判断收束。

- **2 张**：封面结论 → 收束 / 启示
- **3 张**：封面结论 → 核心机制 / 最强证据 → 收束 / 启示
- **4 张及以上**：只有用户明确要求更多页数时再扩展背景、问题和补充证据

默认优先把信息压成短卡组，而不是把同一主题拆成长组图。只有在用户明确要求更多页数，或内容复杂到 `3` 张无法说清时，才扩展到 `4` 张以上。

领域弧线可直接套用：

| 类型               | 默认弧线                                            |
| ------------------ | --------------------------------------------------- |
| 工具 / 产品 / 模型 | 痛点 / 背景 → 核心思路 → 关键能力 / 证据 → 工程意义 |
| 研究 / 论文        | 研究缺口 → 方法创新 → 实验发现 → 为什么重要         |
| 商业 / 新闻        | 反直觉结论 → 背景 → 关键数据 / 对比 → 最终判断      |
| 观点 / 评论        | 核心论点 → 论据 → 张力 / 转折 → 收束                |

### 2.3 信息密度预算

默认要避免两种失败：

1. **太空**：只有标题、一个大图形、几乎没有解释价值
2. **太满**：像 PPT 截图、密集海报或小字图表

**核心原则：每张图必须“把事情说清楚”**——读者只看这张图，就能理解一个完整的信息单元（结论+解释+支撑），而不是只看到一个标签或一个数字。

每张图遵守下列预算：

1. **封面**：`1` 个主结论标题 + `1` 个副标题 / 支持判断 + `1-2` 个关键事实或解释短句 + `1` 个锚点视觉
2. **中间页**：`1` 个核心观点标题 + `2-4` 个短内容块（必须是完整句子或完整判断，不能只是标签） + `1` 个结构化信息块
3. **收尾页**：`1` 个收束标题 + `1-2` 句编辑式 `closing_note` + 可选 `1` 个轻量支撑结构或引用块
4. **每张图视觉上最多 `3` 个主信息区块**；封面和收尾页优先控制在 `2-3` 个
5. **对比项最多 `3` 组，流程最多 `4` 步，时间线最多 `4` 个节点，结构图最多 `4` 层**
6. **每张图至少要有 `标题层 + 说明层 + 结构层` 三种 payload 中的两种**；只有标题和装饰视觉视为失败页
7. 如果某一页必须靠长段落、细小注释或 `4` 个以上 bullet 才能讲清，说明拆页失败，应减少信息或在用户明确要求下增加页数

内容块建议优先使用：

- `headline`：一句结论性标题
- `subhead`：一句补充判断或背景说明
- `support_blocks`：`2-4` 条短说明，每条控制在 `8-30` 个汉字等量信息内；**必须是完整句子或完整判断，不能只是关键词**
- `stat_block`：`1-2` 个关键数字 / 比例 / 年份，必须附带简短解释（如"77.2 > 76.2，超越前代旗舰"）
- `quote_block`：`1` 句冲击性短引语
- `diagram_block`：流程 / 对比 / 分层 / 时间线中的一种

### 2.4 `brief.json` 结构

在输出目录里保存 `brief.json`，至少包含这些字段：

```json
{
  "source_url": "...",
  "topic_slug": "...",
  "format_style": "editorial_information_card",
  "output_language": "zh-CN",
  "density_target": "medium",
  "core_claim": "...",
  "source_points": [{ "point": "...", "role": "mechanism" }],
  "audience": "...",
  "tone": "...",
  "style_direction": "...",
  "publish_title": "...",
  "publish_summary": "...",
  "closing_note": "...",
  "closing_reflection": "...",
  "topics": ["..."],
  "image_backend": "imagegen",
  "cards": [
    {
      "index": 1,
      "role": "cover",
      "density": "medium",
      "card_title": "...",
      "card_subtitle": "...",
      "message": "...",
      "fact": "...",
      "supporting_points": ["..."],
      "data_points": ["..."],
      "content_blocks": ["..."],
      "quote_text": "...",
      "reader_takeaway": "...",
      "diagram_structure": "...",
      "visible_text": ["..."],
      "visual_pattern": "...",
      "visual_direction": "...",
      "prompt": "..."
    }
  ]
}
```

字段说明：

- `core_claim`：整组图只讲一个什么结论
- `output_language`：默认 `zh-CN`；除非用户明确要求其他语言，所有可发布文案和图片可见文字都用简体中文
- `source_points`：从原文压出的 `4-6` 个源要点，供分页和取舍使用；不要直接省略这一步
- `supporting_points`：每页最多 `1-2` 个辅助说明点，避免只有一个裸结论
- `data_points`：适合直接可视化的关键数字、比例、年份、对比事实；优先保留 `1-2` 个最重要的；**必须附带解释，不能裸放数字**
- `card_title` / `card_subtitle`：每页的明确标题层，不要只靠 `message`
- `content_blocks`：每页真正承载信息的 `2-4` 个短内容块，可对应 bullet、对比标签、步骤说明或判断句；**必须是完整句子或完整判断，不能只是关键词**
- `quote_text`：只有在原文里存在足够有力的话时才填写，不要为凑格式硬写
- `reader_takeaway`：用户看完这一页后应带走的判断
- `diagram_structure`：本页适合的信息组织方式，如 comparison / process / layered / timeline
- `visible_text`：**必须包含 `content_blocks` 和 `supporting_points` 中的核心信息**，不能只有标题和标签；读者只读 `visible_text` 应能理解完整信息单元

`topics` 只在来源或内容里有明显话题词时填写；不要臆造热门标签。

## Step 3：为每张图写 prompt

### 3.1 全组共享约束

每张图的 prompt 都要共享同一套视觉系统：

- vertical **4:5** editorial information card / infographic card
- premium editorial composition, magazine-quality layout
- clean grid, generous whitespace
- strong hierarchy, single core idea per card
- **每张图必须同时包含：`1` 个主信息、`1` 组支撑事实、`1` 个解释性结构块；三者合起来必须能独立说清楚一个完整信息单元**
- 默认允许 `2-3` 个主视觉模块，并允许在模块内部承载更多短信息，不要变成密集 dashboard
- 同一主题下保持一致的色彩、材质、镜头语言和版式气质
- 默认适配中文分享场景，图片上的标题、标签、短句和结构说明都必须是简体中文；只保留必要的英文专名、缩写、产品名或模型名
- **不要要求模型渲染长段落文字**，但也不要退化成只有标签
- 明确避免：高密度 PPT、满屏小字、复杂表格、UI 截图、纯风景装饰图

### 3.2 可见文字控制

GPT 生图的文字能力已经够用，但仍然不适合密集排版，所以要主动收敛。但收敛不等于只放标签——**可见文字必须能独立传达完整信息，而不是只有关键词。**

- 默认所有 `visible_text` 使用简体中文，避免英文整句、英文 bullet 和中英混排；英文只用于必要专名（如 OpenAI、MCP、GPT-5）或用户明确要求
- 每张图优先放 **1 个主标题 + 1 个副标题 / 判断短句 + 2-4 个短辅助语 / 说明句**
- 主标题尽量控制在 **6-12 个汉字**
- 副标题尽量控制在 **8-18 个汉字**
- 短辅助语尽量控制在 **4-16 个汉字**，**必须是完整判断句或完整说明，不能只是标签**（如用"27B 稠密模型超越前代旗舰"，而不是"27B / 旗舰"）
- 全图可见文字尽量控制在 **40-80 个汉字等量信息** 内；封面可偏低，中间页可偏高
- 数字、比例必须附带解释（如"77.2 > 76.2，agent 编程新标杆"），不能裸放数字
- 不要要求模型在图中放长网址、脚注、免责声明、细小表格、坐标轴刻度
- 明确写出：**不要出现额外文字、prompt、元数据、水印、UI chrome、二维码、Logo**

如果某张图连续两次都出现明显文字乱码，就减少该页可见文字量，但**不能退化成只有标签**；应改用更短的完整句，或把解释转移到图解结构中，而不是继续堆长文本。

### 3.3 infographic 视觉语法

优先从下面这些模式里选 **1-2 种兼容的组织方式**，让卡片更像真正的信息卡：

- **大数字 + 单一符号主体**：突出一个倍数、比例、年份或结论
- **3-4 步流程**：用箭头或分层示意解释机制
- **A / B / C 对比**：最多 `3` 组对照，不展开成矩阵
- **聚光式指标图**：突出 `1-2` 个数字，并给出简短解释
- **分层 / 结构示意**：把复杂系统压成 `3-4` 层结构
- **轻量时间线**：最多 `4` 个节点，强调转折而非细节编年史

### 3.4 每张图的职责

- **第 1 张（cover）**：必须同时给出 `标题 + 支持判断 + 关键事实 + 解释性短句`，让人只看这张图就能理解核心结论；如果只剩大标题和数字，视为失败
- **中间图**：只在 `3` 张及以上时出现；必须带机制、证据或结构说明，且至少出现 `2` 个有效内容块；**每个内容块必须是完整判断，不能只是标签罗列**
- **最后 1 张（closing）**：收束、判断、启示，不追加无关新事实；优先用 `closing_note` 做编辑式终章，而不是重复前文摘要；**必须包含至少一句让读者带走的核心判断**

如果某张卡片看起来像纯装饰海报，只提供情绪或审美，没有解释性 payload，视为失败页。

**"说清楚"的检查标准**：把 `visible_text` 单独读一遍，如果读者能凭这些文字理解一个完整信息单元（知道"是什么、为什么、意味着什么"），才算合格。

## Step 4：调用生图技能

对 `brief.json` 中的每张卡片，逐张生成图片。

默认顺序：

1. 优先调用 `imagegen`
2. 如果 `imagegen` 明显不可用、连续失败，或用户明确要求 Azure，再回退到 `azure-image-gen`

默认参数：

- `size`: `1024x1280`
- `format`: `png`
- 先用中等质量生成整组
- 输出文件名固定为 `card-01.png`、`card-02.png` ...

只在这些情况下重生成单张卡片：

- 构图明显跑偏
- 可见文字严重乱码
- 风格与整组不一致
- 关键信息点被错误可视化
- 图面太空，信息解释不足

优先单独重生成失败卡片，不要整组全部推倒重来。

## Step 5：快速验收

在进入发布前做一次快速检查：

1. 张数与 `brief.json` 一致
2. 文件顺序正确：`card-01` 到 `card-0N`
3. 每张图都是 **4:5**
4. 没有明显多余水印、prompt 泄漏、UI 壳层
5. 每张图都能看出单独的传播点，而不是重复上一张
6. 中间页不是“好看但空”的海报，能看出明确机制、对比或结构信息
7. 封面不只是一个大词或一个数字，至少能看出结论和支持判断
8. 整体观感像 **信息卡 / infographic card**：能快速扫懂，但没有小字堆砌、复杂表格或密集 dashboard
9. **每张图的 `visible_text` 单独读一遍，能构成完整信息单元（是什么、为什么、意味着什么），而不是只有零散标签**
10. 如果某张图像纯装饰海报却没讲清信息，或者像密集 PPT 截图一样过载，就单独重生成该页

如果只是局部美术不够完美，但信息清楚、顺序正确、可直接发布，就不要无限打磨。

## Step 6：发布

### 6.1 微信公众号

默认进入 `wechat-draft`，用 `newspic` 模式发布同一输出目录：

- `title`：`publish_title` 的压缩版，保证 ≤ 64 UTF-8 字节
- `content`：一句话 `publish_summary`
- `image_dir`：当前输出目录

如果微信凭据缺失，停止在发布阶段并明确说明；不要删除已生成图片。

### 6.2 小红书

默认进入 `xiaohongshu-publisher`，复用同一输出目录：

- `title`：优先保留主体名 + 最强结论
- `description`：2-4 句摘要，可带来源 URL
- `topics`：只使用 `brief.json` 中确认过的话题

如果小红书会话未登录，暂停等待用户登录；不要因为发布受阻而重做图片。

## 向用户汇报

结束时至少告诉用户：

- 输出目录
- 实际生成了多少张图
- 使用了哪个生图后端：`imagegen` 或 `azure-image-gen`
- 是否已发微信草稿箱（`media_id`）
- 是否已发小红书，或者卡在哪一步

## 失败边界

- URL 无法抓取到有效正文：直接失败
- `imagegen` 与 `azure-image-gen` 都不可用：直接失败，不进入发布
- 发布阶段缺少微信凭据或小红书未登录：保留图片，报告发布阻塞
- 用户明确要求“只生成”时：不要触发任何发布 skill

## 触发提示

当用户真正想要的是：

- “把这篇链接做成几张能发出去的图”
- “做成多张小红书 / 公众号分享图”
- “把这个链接做成 infographic / 信息图 / 图卡”
- “把 URL 内容转成 AI 图卡再发布”

就应该优先用这个 `image-card`，而不是 `info-card-designer`。后者适合 HTML 信息卡截图；这个 skill 适合 **原生 AI 生图卡组**。
